## 14:45～15:10 修「被沙虫打死后会报错」（用户反馈）

### 现象与取证
用户只说了句"被沙虫打死后会报错"，没给截图。直接去读运行时日志取证（`%APPDATA%\Godot\app_userdata\loss_land\logs\`），
在 `godot.log` 末尾拿到原文：

```
玩家受到 18 点伤害！剩余生命: -2 / 100
玩家死亡！
SCRIPT ERROR: Invalid access to property or key 'attack_id' on a base object of type 'Nil'.
   at: Sandworm._apply_attack_damage (boss_base.gd:441)
   [1] _process_attack (boss_base.gd:279)   [2] _physics_process (boss_base.gd:164)
```

**先读日志再动代码**这一步是省时间的：报错文件、行号、调用栈一次到位，不用猜。

### 根因（同步重入）
`_apply_attack_damage()` → `body.call("take_damage", _attack.damage)` 这一击把玩家打死：
玩家**同步**发 `died` → `Boss._on_player_died()` → `_start_retreat()` → `_set_state(RETREAT)`
→ 按「离开招式三段就丢掉当前招」把 `_attack = null`，**而扣血函数还没执行完**，
下一行 `attack_landed.emit(_attack.attack_id, …)` 就是空引用。

从旧代码复跑还看到**第二条**报错（`_process_attack` 那行的 `_attack.strike_time`）——
即调用方也接着炸。**真机日志里只有一条**：两条是连续打印的，用户大概率只看到/截了第一条。
⇒ 修的时候不能只修 `_apply_attack_damage`，**调用方也要重新确认**。

### 修法（boss_base.gd，两处）
1. `_apply_attack_damage()`：进函数先 `var attack: BossAttack = _attack`，全程只用局部量 ——
   扣血之后绝不再回头读 `_attack`（命中确实发生了，即使状态已被推去 RETREAT 也该照实上报 `attack_landed`）。
2. `_process_attack()`：`_apply_attack_damage()` 之后 `if _attack == null: return`；
   并在 `match _state` 之前加 `if not BossState.is_attack_phase(_state): return` 守门
   （顺带覆盖"`attack_landed` 监听者反过来打 Boss、把它打进 FALLEN"这类未来扩展）。

### 验证：新旧代码对跑（隔离副本；编辑器开着）
工程复制到 `%TEMP%`、删副本 `.godot` 走全新导入、另设 `APPDATA`。副本里把 `boss_base.gd`
换回 `HEAD` 版本跑新用例 → 复现；再换回修复版跑 → 全绿。

| | SCRIPT ERROR | 用例 13 | 结论 |
| --- | --- | --- | --- |
| 旧代码 | **2 条**（`attack_id` + `strike_time`） | `[失败] 打死玩家的那一击同样上报了 attack_landed（0 次）` | `exit=1`，共 57 断言 1 失败 |
| 修复版 | 0 | 8/8 通过 | `exit=0`，**57/57 全绿** |

配套 `gd_static_lint` 7/7、`check_data_refs` 通过（251 引用 / 物品 30 / 资源 8）。

### 用例 13 的设计要点（值得复用）
- **必须让玩家"死在招式判定里"**：用例 9 用的是外部 `_target.kill()`，不经过招式判定，
  所以它一直测不到这个重入 —— 补的用例要**把血量压到 1、等沙虫的招自己打过来**。
- **断言要选"功能性判据"，不要只看"日志里有没有 ERROR"**：headless 里脚本报错**不会**让退出码非 0。
  这里挂了 `attack_landed` 计数 —— 旧代码在 emit 之前就中断，计数停在 0，用例才真的会红。

### 顺带处理

## 15:20～15:40 修「沙虫经常会变成白色看不清」（用户反馈）

### 取证（这次是**渲染出图**，不是读日志）
用户只说"变白看不清"、没截图。视觉问题不能靠猜 —— headless 渲染不出画面，
所以做了个临时截图工具：**隔离副本 + 窗口跑 `--script`**，冻结 Boss 状态机后固定机位逐状态出图，
**同时把屏幕中心（正对沙虫身体）的像素打进日志**。改前实测：

| 状态 | 取样像素 | 该状态该有的颜色 |
| --- | --- | --- |
| 常态体色 | `#ffffff` | `body_color` (0.82,0.70,0.42) |
| 前摇警示 | `#ffff90` | `telegraph_color` (1.0,0.42,0.22) |
| 濒死 / 退场 | `#ffffff` | `fallen_color` (0.52,0.50,0.55) |
| 地面 | `#ffffff` | 沙色 (0.78,0.68,0.46) |

**全是纯白**：不但沙虫和地面糊成一片，连"前摇变红 / 濒死变灰"这些**状态信号**也一起白掉。

### 根因：环境光过曝，而沙虫是工程里唯一的**受光**网格
`map.tscn` / 场地的环境光是 `ambient_light_color(0.83) × ambient_light_energy(9.0)`
⇒ 受光面整体抬亮约 **2.2 倍**，**albedo 亮过 0.45 的一律打成纯白**。
而**全工程的地形与海面本来就一律 `SHADING_MODE_UNSHADED`**（`map_generator_3d.gd`），
所以这个 9.0 一直无害 —— 直到沙虫这个用默认 `SHADING_MODE_PER_PIXEL` 的网格出现。
沙虫、场地地面、濒死灰的 albedo 全在阈值之上，于是全白；深棕的巢穴土堆（0.35,0.28,0.2）
是唯一没被打爆的（实测 #c9a06a，反证了"抬亮约 2.2 倍"这个模型）。
另：`Visual/Jaw` 连 `material_override` 都没有 ⇒ 走引擎默认的**白色受光**材质，又白一块。

### 修法（三处）
1. `boss_base._setup_placeholder_material()`：材质改 **UNSHADED**；遍历 `Visual` 下**所有**
   `MeshInstance3D` 逐个赋材质（按名字把 `Jaw` 换成暗一档的，新增 `jaw_darken`=0.32）——
   防的就是"以后加零件又漏一个"。
2. 配色：`body_color` (0.82,0.70,0.42) → **(0.58,0.45,0.26) 深沙褐**（地形瓦片色普遍偏亮，
   体色压暗一档才能在**任何**地形上看出轮廓）；`hurt_color` 近白 → **(1.0,0.66,0.52) 暖红**
   （白闪和"被打爆成白"分不清）。
3. 场地：新增 `_ensure_unshaded_materials()` 强制地面/巢穴改 UNSHADED，地面色改为
   **地图"沙地"(13) 的瓦片色**，色号 `preload` `task_system.TERRAIN_COLOR_MAP`（与地图同源）。
   ⚠ 放脚本里而不是只写 `.tscn`：本场景标签页在编辑器里开着，外部改 `.tscn` 会被覆盖（已 3 次）。

### 验证

  濒死 `#857f8c`、地面 `#f2e073`，四个状态互相可分，与目标色逐一吻合。
