## 11:30～11:55 记忆目录合并归档（18 份 → 2 份）

### 起因
用户要求「把 `.workbuddy/memory/` 里的记忆合并到一份 md 里，然后删掉原来的记忆」。

### 关键判断（决定不必做成"严格一份"）
`MEMORY-details.md` 开头自述「2026-09-18 从 `MEMORY.md` 拆出，因为**主文件超出注入预算被截断**」——
即 `MEMORY.md` 是**每轮自动注入**的入口，实测 8.7 KB 刚好在预算内；目录其余内容合计 437 KB。
若把 437 KB 全塞进单个 `MEMORY.md`，注入必然截断，后面 ~97% 内容等于失效。
→ 向用户列出 4 种「一份」的取舍后，用户选定 **全量归档 + 极简指针**。

### 执行
1. **备份**：`cp -r` 整个 `memory/` → `.workbuddy/archive/memory_backup_2026-09-26/`（18/18，文件数校验通过）。
2. **合并**：脚本 `.workbuddy/tmp/merge_memory.py`，把 18 份原文按 A 分区（现行入口快照）/ B（细节详章）/
   C（拆分前全文备份）/ D（每日日志正序）拼进 `MEMORY-archive.md`，并生成 `## 目录`（S01～S18 锚点 + 大小 + 修改时间）。
   输出 461,046 B。
3. **校验**：脚本 `.workbuddy/tmp/verify_memory_merge.py` 解包回读、与源文件**逐字节比对 → 18/18 一致**。
4. **删除**：分 2 批（9 + 8）`rm` 掉 17 个原文件。
5. **改写入口**：`MEMORY.md` 头部指针由 `MEMORY-details.md` 改为 `MEMORY-archive.md`，
   并清掉指向已删文件的悬空引用（三处「→ 详章」改指 `MEMORY-archive.md` S02）。

### 踩坑（可复用）
**校验器比被测物更容易先坏。** 第一版把每份原文包进 ` ```markdown ` 围栏再解包，结果 5 份「不一致」
（09-24 源 19025 字符 / 读回 90 字符）—— 真因是**日志原文自带代码围栏**，解包正则提前收尾，
归档其实完好。改用**哨兵标记** `<!-- BEGIN SRC:<文件名> -->` / `<!-- END SRC:<文件> -->` 包裹后，
解包无歧义，立即 18/18 通过。
→ 教训：做「整体搬迁」类操作，包裹分隔符必须是**正文里不可能出现的形态**，不要用 Markdown 围栏。
